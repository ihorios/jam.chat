# Models and the database

This is the file to read first. Almost everything else in the server is
generated from what is described here.

A **model** is one file in `server/db/models/` that default-exports an instance
of a class extending `Model`. Adding that file gives you tables, indexes,
permissions, REST routes, a repository on both drivers, and a dashboard tab —
with no other edit anywhere.

---

## 1. The registry

`server/db/models/index.js` reads its own directory at import time:

```js
for (const file of fs.readdirSync(__dirname).sort()) {
  if (!file.endsWith('.js') || file === path.basename(__filename)) continue;
  const module = await import(pathToFileURL(path.join(__dirname, file)).href);
  if (module.default instanceof Model) loaded.push(module.default);
}
```

Files exporting something else — the kernel, the catalogue, the field types —
are skipped by the `instanceof` check rather than by a list of exclusions.

Then three things happen, in this order and for a reason:

1. **`sortByDependency`** — a depth-first walk over each model's `requires`,
   throwing on a cycle. Schema creation and seeding both walk the result, which
   is what lets a foreign key assume its target table already exists. Input is
   alphabetical, so the order is stable for models that do not constrain each
   other.
2. **`model.link(models)`** on each — hands every model the finished registry.
   Foreign keys cannot be resolved until every model is known.
3. **`buildCatalog(ordered)`** — permissions exist only because models do.

The resulting order, today:

```
roles → users → files → user_groups → user_messages
```

### `requires` is enforced, not documentation

`link()` checks both directions:

```js
for (const name of this.requires) {
  if (!registry[name]) throw new Error(`Model "${this.name}" requires unknown model "${name}".`);
}
for (const dependency of this.dependencies()) {
  if (dependency === this.name || this.requires.includes(dependency)) continue;
  throw new Error(`Model "${this.name}" points at "${dependency}" but does not list it in \`requires\`.`);
}
```

So a model cannot quietly point at another without declaring it. A model never
has to require *itself* — `user_messages.reply_to` targets `user_messages`.

## 2. Declaring a model

```js
class Widgets extends Model {
  constructor() {
    super({
      name: 'widgets',
      label: 'Widgets',
      requires: ['users'],
      ownedBy: 'owner',
      membership: { via: 'group' },
      actions: ['create', 'read', 'update', 'delete'],
      searchable: ['title'],
      fields: { /* … */ },
      relations: { /* … */ },
    });
  }
}
export default new Widgets();
```

| Key | Meaning |
| :--- | :--- |
| `name` | required; also the REST prefix and the default table name |
| `table` | defaults to `name` |
| `label` | defaults to a titleised `name` |
| `actions` | defaults to all four CRUD actions. `[]` makes the model internal |
| `fields` | physical columns |
| `relations` | side tables |
| `searchable` | field names matched by `?search=` |
| `requires` | models installed first |
| `ownedBy` | the reference field naming the owner — brings `:own` into existence |
| `membership` | how belonging is decided — brings `:member` into existence |

### System columns

Every table carries four columns whatever the model declares, and a model may
not name a field after one of them (the constructor throws):

```js
export const SYSTEM_COLUMNS = Object.freeze(['id', 'uuid', 'created_at', 'updated_at']);
```

`uuid` is generated by the application (`generatedValues()`), not by
`gen_random_uuid()`, so the in-memory driver produces exactly what Postgres
would and the value does not depend on the server version.

## 3. Field types

`server/db/models/fields.js`. Each type maps a declaration to a storage column,
a SQL type, and how a raw client value becomes a stored one.

| Type | SQL | Column | Notes |
| :--- | :--- | :--- | :--- |
| `string` | `VARCHAR(255)` | as named | |
| `text` | `TEXT` | as named | |
| `integer` | `INTEGER` | as named | throws `ValidationError` on non-numbers |
| `boolean` | `BOOLEAN` | as named | accepts `true`, `'true'`, `1`, `'1'` |
| `json` | `JSONB` | as named | serialised on the way out |
| `timestamp` | `TIMESTAMPTZ` | as named | normalised to ISO on both drivers |
| `reference` | `INTEGER` | **`<name>_id`** | needs `target`; `REFERENCES … ON DELETE` |
| `password` | `TEXT` | **`<name>_hash`** | `hidden`; bcrypt cost 10; enforces `PASSWORD_RULES` |

Two types rename their column. `password` renames *and* hides — a hidden field
is left out of every `SELECT` list, which is why the only way to reach a hash is
`findRawBy()`.

### Field flags

| Flag | Effect |
| :--- | :--- |
| `required` | `NOT NULL`, and `parseInput` refuses a blank on create |
| `unique` | `UNIQUE`, plus a `LOWER()` index for text |
| `immutable` | `parseInput` throws on any partial write that names it |
| `privileged` | **stripped from a scoped request body** — see below |
| `index` | asks for an index the rules cannot infer |
| `default` | a literal, or a function evaluated per row |
| `onDelete` | `CASCADE` by default |

`privileged` is the flag that makes own-scoped writes safe to grant. Editing
your own profile should mean "fix your name", never "promote yourself".
`routes/crud.js` deletes these keys from the body of any scoped request. On
`users` they are `email`, `password`, `is_active`, `email_confirmed`, `logo_file`
and the `roles` relation.

### Defaults

A declared default may be a literal or a function. A function is evaluated per
row **by the application**, which is how a value like "now" stays identical on
both drivers instead of depending on a SQL default the memory store cannot
apply. `defaultClause()` emits `DEFAULT x` only for literals.

### Password rules

```js
export const PASSWORD_RULES = Object.freeze([
  { id: 'length', label: 'at least 8 characters', test: (v) => v.length >= 8 },
  { id: 'letter', label: 'a letter',              test: (v) => /[A-Za-z]/.test(v) },
  { id: 'digit',  label: 'a digit',               test: (v) => /\d/.test(v) },
  { id: 'symbol', label: 'a special character',   test: (v) => /[^A-Za-z0-9]/.test(v) },
]);
```

Enforced in the *field type*, not in the registration route, so it also covers
admin-created users, password changes and the boot-time admin seed. A rule that
only lives in a form is not a rule. `src/lib/password.js` mirrors these for live
feedback while typing; this copy is authoritative.

## 4. Relations

Two kinds, both stored in a side table rather than a column, so both are
resolved by the repository rather than by the `SELECT` list.

### `manyToMany`

```js
roles: { type: 'manyToMany', target: 'roles', through: 'user_roles', privileged: true }
```

Defaults: `through` is the two model names sorted and joined; `localKey` is
`<singular(model)>_id`; `targetKey` is `<singular(target)>_id`. Both columns
cascade, and the primary key is the pair.

### `permissionSet`

```js
permissions: { type: 'permissionSet' }
```

A set of grants stored as `(owner_id, model, action, scope)` with that
four-column primary key. Only `roles` uses it.

### Columns on the link row

A `manyToMany` may declare columns of its own — data belonging to the **pair**
rather than to either end of it:

```js
members: {
  type: 'manyToMany', target: 'users', through: 'user_group_users', privileged: true,
  columns: { last_read_at: { type: 'timestamp' } },
}
```

How far somebody has read in a group is the one today, and it is the example
worth understanding: it is neither a fact about the user nor about the group but
about their membership. Keeping it there buys three things a table of its own
could not.

| | |
| :--- | :--- |
| **uniqueness** | the pair is already the primary key, so a second marker for the same person in the same group cannot exist |
| **cleanup** | leaving takes it away, because the link row cascades — no hand-written tidying, and no stale marker waiting to mark a conversation read that nobody read |
| **one lookup** | `readLinks('members', { target: userId })` answers "which groups, and how far into each" in a single indexed read |

**Declaring `columns` changes how the relation is written.** A relation without
them is replaced wholesale on every write — `DELETE` everything, re-`INSERT` the
submitted list — which is right when the rows hold nothing but the two keys, and
is exactly what would erase this: every invitation rewrites the whole member
list, so everybody's read position would reset whenever anyone joined. A
relation that carries payload is **reconciled** instead: rows no longer in the
list go, new ones are inserted, and the ones that survive are left untouched.

Two repository methods come with it, on both drivers:

| | |
| :--- | :--- |
| `readLinks(name, { owner, target })` | link rows by either end, payload included |
| `writeLink(name, owner, target, values)` | writes payload onto one existing row; **`false` when there is none** |

`writeLink` returning `false` is the membership check falling out of the write
itself — marking a group read that you are not in is not so much refused as
impossible, and costs no extra query to establish. It never creates the link:
joining is a membership change, and this is not one.

## 5. Ownership and membership

These two declarations are what make scoped permissions possible. They are
independent: a group's owner is one user, its members are many, and either may
be granted alone.

**`ownedBy: 'owner'`** names a reference field. It brings `<model>:<action>:own`
into existence, and `ownerColumn` is what an own-scoped query filters on.

`users` is the interesting exception — ownership there is *identity*, not a
foreign key, so it declares no `ownedBy` and overrides both halves directly:

```js
get ownerColumn() { return 'id'; }
ownedByUser(row, userId) { return Boolean(row) && Number(row.id) === Number(userId); }
```

**`membership`** takes one of two shapes:

| Shape | Meaning | Used by |
| :--- | :--- | :--- |
| `{ relation: 'members' }` | the users in this many-to-many are its members | `user_groups` |
| `{ via: 'group' }` | membership is whatever the referenced row says | `user_messages` |

`{ via: 'group' }` is what makes `user_messages:read:member` mean "everything
said in the groups you are in" — *including what other people said*, which is
the whole point of a conversation.

Both are validated in the constructor: `relation` must name a `manyToMany`,
`via` must name a `reference`, and at least one must be present.

## 6. Hooks

| Hook | When | Notes |
| :--- | :--- | :--- |
| `seed(repositories, log)` | every boot, in dependency order | must be idempotent; gets the *full* repository set |
| `transform(row)` | on the way out of the repository | |
| `beforeDelete(row)` | before the delete | **awaited**; throw to veto, and nothing is touched |
| `afterDelete(row, ctx)` | after the delete succeeded | awaited; `ctx.getRepo(name)` reaches other repositories |
| `parseInput(input, opts)` | on every write | override to add normalisation |
| `permissions()` | at catalogue build | override to grant something other than the default |

`afterDelete` receives the row **hydrated, as it was** — relations still visible
even though the link rows have just cascaded away. That is the only moment a
model can still see what it carried. Throwing there would report a delete that
happened as one that did not, so implementations swallow their own errors and
log.

Two models use it:

- `files` nulls any `users.logo_file` still pointing at the row — `ON DELETE SET
  NULL` written out by hand, because `logo_file` is a plain integer rather than
  a foreign key (a key back to `files` would be a cycle the schema cannot
  create). Its **object** is deleted from `beforeDelete`, not here: see
  [Files and S3 §7](file.md#7-the-sweep).
- `user_messages` deletes attachments that no *other* message still uses.

## 7. Generated DDL

`Model#schema()` returns the model's own `CREATE TABLE IF NOT EXISTS` followed
by one per relation. `Model#indexes()` is separate, because a column added to an
existing table cannot be indexed in the same pass that adds it.

Three index rules, each answering a query the application actually makes:

| Rule | Why |
| :--- | :--- |
| every `reference` column | Postgres does not index a foreign key on its own. `ON DELETE CASCADE` has to find children — without it, deleting a group reads *every message in the database*. Same columns the scoped filters compare against |
| the `targetKey` of every `manyToMany` | the link table's PK is `(local, target)`, which serves lookups by the local side and nothing by the target side — and the target side is the hot one ("which groups is this user in") |
| `LOWER()` of every unique text field | `findRawBy` compares case-insensitively, so the plain btree `UNIQUE` built cannot serve it. That is the query behind every sign-in |

A unique column already has a btree from the constraint, so no second plain
index is created for it. A field may also ask for one with `index: true` —
`users.logo_file` is the only one today.

**Deliberately not generated:** an index for `?search=`, which is
`ILIKE '%term%'` and would want a `pg_trgm` GIN index. That needs an extension
the server may not be allowed to create, so it is left to whoever runs the
database.

## 8. Schema reconciliation

`server/db/schema.js` runs `syncSchema()` on every boot. It is not a migration
framework — it is a reconciler.

**Pass one:** every model's `schema()`, in registry order.

**Then the catalogue, once:**

```js
const columns = await columnsByTable();   // one query for every column of every table
const indexes = await existingIndexes();  // one query for every index name
```

One query rather than one per table, and the reason is latency rather than
tidiness: boot cost here is round trips, not rows. A managed database is
routinely 150 ms away, so the difference between one read of the catalogue and a
dozen is the difference between a boot and a timeout.

**Pass two,** per model:

1. `ensureUuidColumn` — adds `uuid`, backfills existing rows one at a time with
   application-generated values, *then* applies `NOT NULL` and `UNIQUE`. Only
   constrain once every row satisfies the constraint.
2. `syncColumns` — adds columns declared on the model but missing from the
   table. **New columns are always nullable, even when the field is required**:
   an existing table may hold rows with no value, and a `NOT NULL` without a
   default would fail outright. `addColumnDefinition()` exists for exactly this,
   dropping `NOT NULL` and `UNIQUE` that `columnDefinition()` would have added.
3. `migratePermissionScope` — adds `scope` to a `permissionSet` table that
   predates scoped permissions, and rebuilds the primary key to include it.
   Everything already stored was unscoped, which is what `any` means, so the
   default backfills correctly.
4. Indexes, skipping ones already present. `IF NOT EXISTS` makes a statement
   safe, not free.

**Finally,** `migrateLegacyUserColumns` moves data off a pre-refactor schema —
`users.role` into `roles`+`user_roles`, `users.name` split into
`first_name`/`last_name`, and `users.permissions` renamed to
`legacy_permissions` and made nullable. Per-user permissions have no home in the
new model, so the data is preserved rather than destroyed, and a warning says to
drop the column once reviewed. All three are idempotent — they only act while
the legacy column is still present.

## 9. The two drivers

`server/db/repository.js` builds one repository per model on whichever driver is
live. Routes talk to repositories only, so they are unaffected by which.

```js
const create = isPostgres() ? createPgRepository : createMemoryRepository;
```

`getRepo` is passed in as a closure rather than a finished map, so relations can
point at models that have not been constructed yet.

### Choosing a driver

`server/db/index.js`:

- **No connection string** → `false`, and the in-memory store. This is not a
  failure; it is how a checkout runs with no database at all.
- **A connection string that cannot be reached** → **throws**. This used to fall
  back to the same in-memory store, which booted an application that looked
  entirely healthy, accepted writes, and lost every one of them on the next
  restart. `plugins/db.js` catches it and records the subsystem as down.

That asymmetry is the single most important decision in the data layer, and the
file storage makes the same one in production. See
[Fastify §4](fastify.md#4-subsystems-and-staying-up).

TLS is left to the connection string: `pg` parses `DB_STRING` after the pool
options, so its `sslmode` wins. A hosted database wants `sslmode=verify-full`.

### The repository interface

| Method | Notes |
| :--- | :--- |
| `findAll({ search, owner, member, match }, depth)` | the scoped filters live here; `match` narrows by foreign key |
| `findByIds(ids, depth)` | |
| `findById(id, depth)` | |
| `findRawBy(field, value)` | **raw row, hidden columns included** — the only way to a password hash. Case-insensitive for text. Never hand the result to a client |
| `isMemberOf(id, userId)` | |
| `linkedTargets(relation, ids)` | which of these targets is *still* linked to anything |
| `countNewer(field, buckets, opts)` | grouped counts and the newest row per group, as an aggregate |
| `create(input)` / `update(id, input)` | transactional; relations replaced wholesale |
| `remove(id)` | hydrates, runs `beforeDelete`, deletes, runs `afterDelete` |

`DEFAULT_DEPTH = 2` — deep enough for `users → roles → permissions`.
`depth: 0` returns relations as empty arrays, which is what the hot paths
(`unreadFor`, the sweep) use to avoid hydrating what they will not read.

`linkedTargets` is the one question a many-to-many cannot be asked from the
owning side: not "what does this row point at" but "is anything *else* still
pointing at these". It goes to the link table directly, because the alternative
is reading every row of the model and hydrating each — a whole-table scan to
answer a question about three ids.

### Unique violations

`asFriendlyError` turns Postgres `23505` into a `ValidationError` naming the
field: *"A User with that email address already exists."*

## 10. Seeding

`server/db/seed.js` walks the registry in dependency order and calls each
model's `seed()`. Every seed runs on **every boot**, not just the first — it is
what keeps derived defaults in step with the registry as models come and go.

Two models seed:

- **`roles`** — creates `admin`, `moderator` and `user` if absent. Only `admin`
  self-heals (its permissions are refreshed from the catalogue whenever they
  drift), because the others may have been edited deliberately. A `BACKFILL` map
  additively grants permissions added to a default role's definition *after* the
  row first shipped. `moderator` also carries `renamedFrom: 'editor'`, renaming
  the old row rather than leaving it beside a new one.
- **`users`** — the first account, from `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
  **Created only when the address is free, and an existing row is never
  touched** — this runs on every boot, so a seed that rewrote the configured
  password each time would silently undo the password change the account exists
  to receive. Nothing is seeded unless both variables are set.

The admin password still has to satisfy `PASSWORD_RULES`: the seed goes through
the model like every other write. A failure is logged as a warning and the boot
continues, because that is configuration rather than a bug.

## 11. The five models

| Model | Owned by | Membership | Actions | Notes |
| :--- | :--- | :--- | :--- | :--- |
| `roles` | — | — | CRUD | `is_system` rows cannot be deleted |
| `users` | *identity* | — | CRUD + `update:own` | id 1 cannot be deleted |
| `files` | `owner` | — | R/U/D **+ `create` permission** | no create *route* |
| `user_groups` | `owner` | `{relation: 'members'}` | CRUD | `members` is privileged; `:member` for `read` only |
| `user_messages` | `owner` | `{via: 'group'}` | CRUD | `system` field is privileged; `:member` for `read` and `create` |

36 permissions in total. Two things there are worth a second look:

**`files` declares a `create` permission without a `create` action.** Declaring
the action would generate a JSON create route, and a row that named its own
`provider_id` without uploading anything would point at somebody else's bytes.
Declaring only the permission gives the upload route something to guard on and
the roles screen something to grant. The catalogue reads `permissions()` rather
than the action list, which is exactly what it is for.

**Both messenger models withhold most of their `:member` permissions.** A
`membership` declaration makes `:member` answerable for all four actions, and
most of those should not exist — `user_groups` publishes it for `read` alone,
`user_messages` for `read` and `create`. Being in a group is grounds for seeing
the conversation, not for rewriting other people's words in it, ending it, or
taking it. See
[Permissions §2](permissions.md#2-where-scopes-come-from) for what each withheld
one would have meant.

A model may also declare `actions: []`, which gives it a table, a repository
and the schema treatment but no routes and no permissions — bookkeeping rather
than something to administer. `permissionsByModel()` filters out models granting
nothing, and `/api/meta` filters out models with no actions, so such a model
never reaches the dashboard. None is registered today: read position, which used
to be one, now lives on the membership relation instead (§4).

## 12. Adding a model

```js
// server/db/models/widgets.js
import { Model } from './model.js';

class Widgets extends Model {
  constructor() {
    super({
      name: 'widgets',
      requires: ['users'],
      ownedBy: 'owner',
      searchable: ['title'],
      fields: {
        owner: { type: 'reference', target: 'users', required: true },
        title: { type: 'string', required: true },
        secret: { type: 'text', privileged: true },
      },
    });
  }
}

export default new Widgets();
```

Restart. You now have: a `widgets` table with an index on `owner_id`; eight
permissions (four actions × two scopes); `GET/POST/PUT/DELETE /api/widgets`,
guarded; both repositories; an entry in `/api/meta`; and a dashboard tab with a
generated form. `secret` is invisible to an own-scoped writer.
